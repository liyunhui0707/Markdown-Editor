## 检查点与提交

- 在一个可说明、可回退的实现边界通过相关检查后建立提交，不等到多组功能累积。
  切换大功能组、长时间测试或交接前，先处理工作区状态。
- 可以在当前任务明确授权下建立本地 WIP 检查点；标明未完成测试及限制。
  WIP 不等于可合并、可安装或可发布。
- 提交前检查实际 diff、暂存清单、生成产物和相关测试。只暂存本任务文件，
  不将不相关修改一起收拢。提交信息说明具体行为或问题。
- 凭据、用户文档、私有配置、`.local/`、依赖和运行日志不进入 Git 或 App。
  私有归档不等于远端备份；已授权的源码应及时推送到唯一 origin。

## PR、CI 与交付

1. PR 围绕完整功能组或一个明确问题，说明结果、验证和实际限制。
2. 本地运行与改动相称的检查；复用同一源码的可靠证据，不为文档改动要求人工输入验收。
   完整 CI 如被仓库配置触发或要求，须等待通过，不跳过失败门槛。
3. 合并前核对最终 head/base、CI、冲突及未解决审核；使用已审查 head 防止误合并新提交。
   CI 通过不替代真实输入、旁白、持续写作或发布验收。
4. 日常 App 可在匹配源码的本机相关测试、候选启动和安装包完整性检查通过后更新，
   不以 CI 完成为前提。更新前保留回退副本、确认用户正常退出，并核对实际安装包。
   CI 在后台继续；已知数据、安全或相关功能回归仍须先修复。合并和正式发布沿用其
   所需检查。无需产品更新的文档/Git 收尾不重装 App。
5. 合并后核对远端合并状态，再将干净的本地 main 快进同步；确认改动已包含且没有遗留 WIP。
   发生主线变化时重新检查，不能用硬重置或强推掩盖差异。

## 分支收尾

2026-11-18 用户进一步明确：CI 不作为替换日常 App 的先决条件。本机测试与固定
产物核对可支持安装更新；此决定不把未执行的 CI 记为通过，也不取消合并/发布检查。

- 在当前任务授权包含清理时，合并后的功能分支应在本组收尾，不无限积累。
  缺少授权时记录待清理项；已有明确授权不逐个重复询问。
- 先记录分支名和 SHA，核实其提交已被 main 包含、没有活动 PR、未被其他 Worktree 使用。
  无法确认的分支保留；恢复分支、main、未合并工作和标签不按名称或年龄批量删除。
- 本地使用正常的已合并分支删除；远端删除限定到核实过的具体引用，并校验预期 SHA，
  防止其他会话新推送的工作被清理。不得把本轮授权扩大成强推历史或删除其他仓库。
- 收尾记录放在既有私有 QA/整理目录。需要恢复时根据映射与 Git bundle 检查，
  不直接重跑使用旧绝对路径的脚本。

## 版本与标签

- `apps/desktop/package.json` 是应用版本源；锁文件的根版本保持一致。
  行为修复升 patch，完整新功能组升 minor；文档、Git 整理和无行为内部修改不自动升版。
- 开发候选用版本号、提交 SHA、PR 和安装包哈希定位。每次合并或版本变化都打标签会
  混淆开发与发布；不再要求这样做，也不批量补打历史候选版本。
- 仅在明确接受的里程碑或发布上建立带说明的 `v<应用版本>` 标签，指向核实过的 main
  提交。标签推送仍需本次任务明确授权，只推该标签；不得移动、覆盖或删除已有标签。
- 现存 `v0.17.3` 保持原样。标签不自动创建 GitHub Release，不代表通过签名、公证或
  真实日用验收；公开交付另按当时的产品决定进行。
